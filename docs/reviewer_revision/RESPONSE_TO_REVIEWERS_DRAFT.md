## General response

We thank the reviewers for their careful assessment. We agree that the initial manuscript did not sufficiently document the simulated dataset, sensor assumptions, target normalization, warning-event definitions, and the limits of the short warning lead times. We are revising the paper to distinguish point-wise forecasting accuracy from event-level advance-warning utility, to avoid implying that simulated results establish real-vehicle safety, and to report the model's trade-offs rather than a single aggregate “best” model.

The repository currently contains an event-level evaluator that extracts 39 instability events and counts a warning as an early detection only if the warning begins before or at event onset and no more than 5 s before onset. Warnings beginning after onset are counted separately as late-only. In the latest local output, early detections range from 24/39 to 29/39 (61.5%–74.4%), with median lead times from 0.50 to 0.90 s and 6–20 unassociated warning episodes across model/horizon combinations. These figures supersede the old approximately 97% event-detection figures only after the final manuscript adopts and documents this current evaluation protocol consistently. They are simulation results, not real-world validation.

### Comment 1 — Dataset and sensor documentation

**Reviewer request:** Describe whether the data are real or simulated, vehicle, sensors, rate, features, event/label definition, class balance, and run counts per surface.

**Response draft:** We agree. The data are generated by a nonlinear two-degree-of-freedom bicycle-model simulator with representative Pacejka tire curves; they are not measured vehicle data. The simulator internally integrates at 100 Hz and exports aligned samples at 20 Hz. The four model inputs are measured yaw rate, lateral acceleration, longitudinal speed, and steering angle. The forecasting target is a simulated rear-axle tire-saturation-margin proxy at 0.5, 1.0, and 2.0 s. The split is by complete run (201 train, 43 validation, 44 test runs), not by overlapping windows. We will add class/event counts and run counts by surface from the actual metadata and test split.

## Reviewer #6

### Comment 1 — Hardware, sensor configuration, beta and yaw-rate estimation

**Response draft:** We will identify the four assumed low-cost channels and state that the current data are simulated sensor streams with illustrative noise and quantization, not logs from a specified commercial sensor kit. Yaw rate and lateral acceleration are direct simulated sensor channels; longitudinal speed is treated as a wheel-speed-derived measurement; steering angle is the retrofit steering input. The current model does not directly measure lateral velocity. Any beta estimate obtained by integrating lateral acceleration minus the kinematic yaw term can drift and must be described as an approximate observer, not a direct sensor measurement.

**Outstanding evidence:** Add exact sensor noise/quantization settings from the source code and clarify whether steering and speed channels are physically instrumented or only simulated.

### Comment 2 — Forecasting target, units, normalization and metric meaning

**Response draft:** The target is a dimensionless normalized rear-axle slip-margin proxy, derived from the difference between the simulator's peak rear-tire slip angle and the simulated rear slip angle, normalized by that peak. MAE and RMSE therefore measure error in this dimensionless margin, not directly in degrees, yaw rate, probability of collision, or rollover risk. R² is a relative goodness-of-fit measure and does not alone establish safety utility. The revised manuscript will document the target equation, sign convention, scaling, and any model-input normalization separately.

**Progress / remaining evidence:** The updated reviewer-revision script checks that prediction arrays and target arrays have identical shapes and computes metrics directly on the saved target scale. Run it successfully and reconcile any remaining old tables before submission.

### Comment 3 — Validation threshold selection and trade-off

**Response draft:** Thresholds are selected from validation predictions only. The current calibration code searches a threshold grid from −0.50 to +0.50 in 0.05 increments and uses sustained-warning grouping (two consecutive samples; 0.20 s warning-gap parameter; maximum 5 s pre-event association window). The manuscript will specify the exact selection objective and tie-breaking rule from the calibration implementation, and will discuss the missed-event/false-warning trade-off rather than implying that calibration eliminates false alarms.

**Outstanding evidence:** Verify and quote the exact objective and tie-breaking code before finalizing this response.

### Comment 4 — Persistence has lower RMSE/R² discrepancy at 0.5 s

**Response draft:** We agree that this apparent discrepancy requires verification. MAE and RMSE weight errors differently: RMSE penalizes large errors more strongly, so their rankings can differ. However, this general property does not establish that the reported table is correct. We will recompute MAE, RMSE, and R² for all models from the same test targets, using the same horizon alignment and target scale, then replace the table only after the calculations agree.

**Progress / remaining evidence:** The reviewer-revision script now constructs a persistence reference prediction from the current simulator margin and a separate sensor-only physics-observer prediction, then evaluates both on the same held-out target arrays as XGBoost/LSTM/GRU/Hybrid. The revised script must still be run successfully and its output checked before replacing the stale comparison table.

### Comment 5 — Definitions of point-wise instability, events, warning episodes, false warnings, lead time

**Response draft:** The current simulator defines instability using a sustained negative-margin condition (three consecutive samples at the 20 Hz output rate). The event-level evaluator extracts contiguous true-flag intervals within each run. Warning episodes are formed from predicted margin crossings below the selected threshold, require two consecutive warning samples, and are grouped using the configured 0.20 s gap rule. A warning is early only if its onset is no later than event onset and falls within the 5 s relevance window; a warning after onset but before event end is late-only. An unassociated warning episode is not matched to any event. Point-wise metrics evaluate individual samples, whereas event metrics evaluate whether an episode gives advance notice of an event; consequently, their rankings need not agree.

**Outstanding evidence:** Ensure the manuscript states whether event extraction uses the raw instability flag or a smoothed flag, and use the same definition across all reported tables.

### Comment 6 — Short lead time and zero median in the old paper

**Response draft:** We agree that short or zero median lead time limits practical usefulness. The current evaluator's median lead times are 0.50–0.90 s among early-detected events, but these are conditional on successful early detections and do not imply every event receives a warning. We will remove any implication of sufficient driver-reaction time and explicitly state that no real driver-response, HIL, or vehicle-control validation has been performed. The old zero-median statistic will not be mixed with the current evaluator without explaining the changed definition.

### Comment 7 — Uncertainty and generalization

**Response draft:** We will report the number of independent runs and the run-level split, and clearly limit conclusions to the evaluated simulated conditions. The current 44-run test set does not establish transfer to other vehicles, payloads, surfaces, sensor hardware, or driving populations. Run-level bootstrap intervals and multi-seed retraining are planned and will be reported only after execution.
